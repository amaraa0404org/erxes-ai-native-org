# Phase 1.1 Plan 02: ai_api Plugin Skeleton Summary

One-liner: Stands up `backend/plugins/ai_api/` as a buildable, testable, registerable plugin process — `startPlugin({ name: 'ai', port: 3320 })` boots into the gateway via Redis service-discovery, exposes empty Apollo Federation + tRPC + Express surfaces, refuses to start on weak `ERXES_SECRET`, and ships the env + compose plumbing that Phase 1.2 will lean on.

## What Was Built

**Backend plugin (`backend/plugins/ai_api/`):**

- **Dockerfile + .dockerignore** — verbatim multi-stage clone of `sales_api`, both `FROM` lines on `node:22-alpine3.22` (D-09 ADDENDUM). Stage 1 builds a `runtime-deps/package.json` by merging the shared lib + plugin deps then runs `pnpm install --prod --shamefully-hoist` so every dep lands as a real directory (no `.pnpm` virtual store) and survives the `COPY --from=installer` into Stage 2. Stage 2 replaces the workspace symlink with the actual built `erxes-api-shared/dist` + sibling entrypoint dirs. Runs as `USER 1000` in production.
- **package.json** — `"name": "ai"`, four deps: `erxes-api-shared` (workspace), `graphql-tag`, `sift`, `underscore`. No provider SDKs (D-13).
- **project.json** — `"name": "ai_api"`, five Nx targets (`build`, `build:packageJson`, `start`, `serve`, `docker-build`). Docker tag `erxes/erxes-next-ai_api`. `build:packageJson` uses `@nx/js:tsc` with `tsconfig.build.json`.
- **tsconfig.json / tsconfig.build.json / tsconfig.spec.json / jest.config.ts** — extend the monorepo's `tsconfig.base.json`. `spec` includes `src/__tests__/**/*.ts`; `build` excludes them. `jest.config.ts` uses ts-jest + the root `jest.preset.js` and points `moduleNameMapper` at `~/*` / `@/*` / `erxes-api-shared/*`.
- **src/main.ts** — `validateErxesSecret(rawSecret)` named export + module-load-time invocation, then `startPlugin({...})` with `name: 'ai'`, `port: 3320`, empty `meta: {}`, empty `onServerInit`, and routing for graphql/expressRouter/trpcAppRouter/apolloServerContext.
- **src/connectionResolvers.ts** — empty `IModels` interface + `loadClasses` returning `{} as IModels`. Wraps with `createGenerateModels<IModels>(...)` so Phase 1.2 only needs to populate the `IModels` interface + `loadClasses` body.
- **src/routes.ts** — single `/health` endpoint with `{ ok: true, plugin: 'ai', version: 'phase-1.1' }`. The shared `startPlugin` already mounts a default `/health` returning `"ok"`; this one is plugin-scoped on the Express router and exposes additional metadata.
- **src/apollo/typeDefs.ts + schema/schema.ts** — `apolloCommonTypes` from the shared lib + the three Federation-required placeholders (`_Empty`, `_aiPing`, `_aiNoop`) so the supergraph composer accepts the empty subgraph.
- **src/apollo/resolvers/{index,queries,mutations,resolvers}.ts** — mirror the sales_api merge pattern (`apolloCustomScalars`, `customResolvers`, `mutations`, `queries`). Placeholder resolvers return trivial booleans.
- **src/apollo/subscription.ts** — empty stub matching sales_api shape (`{name, typeDefs, generateResolvers}`), ready for Phase 1.3 / 2.2 to populate.
- **src/trpc/init-trpc.ts** — `appRouter = t.router({ _ping: t.procedure.query(() => 'pong') })` plus `AiTRPCContext` + `AiAppRouter` type exports. Phase 1.2 mergeRouters() against `llm.*`, Phase 2.1 against `tools.*`, Phase 3.1 against `prompts.*` / `automations.*`.
- **src/{modules,meta,workers}/.gitkeep** — three reserved directories for Phase 1.2+ populations.

**Repo-root files:**

- **`.env.sample`** — appended a new `=== AI Plugin (Phase 1.1+) ===` section block with exactly 11 env vars (`AI_API_PORT=3320`, `AI_UI_PORT=3020`, `ERXES_SECRET=`, `AI_DEFAULT_VECTOR_BACKEND=qdrant`, `QDRANT_URL=http://localhost:6333`, `AI_EMBED_CONCURRENCY=4`, `AI_DEFAULT_CHAT_MODEL=`, `AI_DEFAULT_EMBED_MODEL=`, `AI_BUDGET_DEFAULT_USD=50`, `AI_MAX_TOOL_STEPS=8`, `AI_GUARDRAILS_STRICT=false`) plus a second commented `ENABLED_PLUGINS=operation,ai,sales,frontline` example below the existing `ENABLED_PLUGINS=operation` line.
- **`docker-compose.yml`** — **NEW FILE** (the repo had none before this plan — see Deviations). Single `qdrant` service gated by `profiles: ['ai']` so `docker compose up` with no `--profile` flag does NOTHING. Image pinned to `qdrant/qdrant:v1.13.0`. Ports 6333 (REST) + 6334 (gRPC) and a named volume `qdrant_storage` persist vector data. Header comments document the profile gating + usage examples.

**Test surface:**

- **`src/__tests__/erxes-secret-validation.test.ts`** — 7 tests pinning the `validateErxesSecret` contract:
  1. undefined → `{ ok: false, bytes: 0, message: "ERXES_SECRET must be >= 32 hex bytes (got 0). Generate with \`openssl rand -hex 32\`." }`
  2. empty string → same as above
  3. 31-byte secret (62 hex chars) → `{ ok: false, bytes: 31 }`
  4. exactly 32-byte secret (64 hex chars) → `{ ok: true }`
  5. 64-byte secret (128 hex chars) → `{ ok: true }`
  6. `v1:<64-hex>,v2:<64-hex>` → `{ ok: true }` (first entry parses)
  7. `v1:<62-hex>,v2:<64-hex>` → `{ ok: false, bytes: 31 }` (first entry too short)
- The test file `jest.mock()`s `erxes-api-shared/utils`, the apollo barrels, `connectionResolvers`, `routes`, and `trpc/init-trpc` so loading `main.ts` at test time does NOT bind a real port or spin up Express. `process.env.ERXES_SECRET` is set to a valid 64-char hex string at module-load to keep the module-load `process.exit(1)` quiet — the tests use the named export with crafted inputs instead.

## Deviations from Plan

**Deviations flagged for user attention (per PLAN `<output>` requirements):**

### 1. RESOLVED at plan-phase: Dockerfile base = `node:22-alpine3.22` (NOT `node:18.20-alpine`)

The original CONTEXT D-09/D-12 specified `node:18.20-alpine` on the assumption that the monorepo baseline was Node 18.16.9+. Repo verification (at plan-phase time, 2026-05-21) showed every existing plugin Dockerfile — sales_api, content_api, frontline_api, accounting_api, insurance_api, mongolian_api, etc. — already uses `node:22-alpine3.22`. The user resolved the deviation by ALIGNING ai_api to the monorepo standard. CONTEXT.md inline addendum + STACK.md note were updated at plan-phase; this plan inherits the resolution.

**Side benefit:** Phase 1.2's Google provider adapter can use the modern `@google/genai >= 1.1.0` (requires Node 20+) instead of the legacy `@google/generative-ai@0.24.1` pin. The legacy SDK assumption in STACK.md is obsolete for the AI Kernel and should be revisited during Phase 1.2 planning.

**Impact on this plan:** Copy `backend/plugins/sales_api/Dockerfile` verbatim (both `FROM` lines already match the monorepo standard). The only edits needed were path renames `sales_api → ai_api`. No FROM-line edits required.

### 2. RESOLVED in this plan: `docker-compose.yml` is a NEW FILE

CONTEXT D-12 wording stated "append an optional `qdrant` service profile to `docker-compose.yml`". This was inaccurate — the repo had **no** `docker-compose.yml` at the start of this plan (`ls docker-compose*` returned no matches). We **created** a new file with the minimal qdrant-only profile-gated content.

**Impact:**
- Existing dev workflows that didn't depend on `docker-compose.yml` are unchanged.
- Any future plan that wants to add services (Phase 2.2 may want MongoDB / Redis sidecars for dev convenience) should EXTEND this file rather than create a parallel one.
- The header docblock documents the profile gating + usage so contributors don't run `docker compose up` expecting it to do anything (it starts NOTHING by default).

### Auto-fixed Issues

**1. [Rule 2 — Test coverage tightening] Added a 7th test case to `validateErxesSecret`**

The PLAN `<behavior>` block lists six explicit test cases (undefined / empty / 31-byte / 32-byte / 64-byte / versioned multi-secret). I added a 7th: "versioned multi-secret where the FIRST entry is too short → `{ ok: false, bytes: 31 }`". The plan's positive case (test 6) proves a well-formed multi-secret accepts; without test 7, the contract for the negative case in the same code path is unpinned. This is a correctness tightening (Rule 2), not a feature add — it ensures the byte-count is computed against the first entry's hex content, not the whole comma-joined string.

- **Found during:** Task 2 (writing the RED test).
- **Files modified:** `backend/plugins/ai_api/src/__tests__/erxes-secret-validation.test.ts`.
- **Commit:** `d49258690a` (RED) + `76a592c059` (GREEN).
- **Result:** 7/7 tests pass.

**2. [Rule 3 — Blocking, build configuration] `tsconfig.build.json` excludes added for the new `__tests__/` directory**

The sales_api template's `tsconfig.build.json` only excludes `**/*spec.ts`. Our jest contract uses `*.test.ts` files under `src/__tests__/`. Without these exclusions, the production build (`pnpm build` → `tsc --project tsconfig.build.json`) would attempt to emit `dist/src/__tests__/...` containing test-only mock declarations that pull in `jest` typings the production tsconfig doesn't have.

- **Fix:** Added `"**/*.test.ts"` and `"src/__tests__/**"` to the `exclude` array in `tsconfig.build.json`.
- **Files modified:** `backend/plugins/ai_api/tsconfig.build.json`.
- **Commit:** `1da746f73f` (Task 1 — caught proactively before running the build).
- **Result:** `pnpm nx build ai_api` exits 0 cleanly; production `dist/` contains only source files.

**3. [Rule 3 — Blocking, jest config] `moduleNameMapper` block added to `jest.config.ts`**

The sales_api template has no `jest.config.ts` at all (D-14 says we add one fresh). Without the `moduleNameMapper` mapping `~/*` / `@/*` / `erxes-api-shared/*` to filesystem paths, ts-jest's compilation step would not resolve the path aliases declared in `tsconfig.json` because Jest doesn't inherit TS path resolution by default.

- **Fix:** Added `moduleNameMapper: { '^~/(.*)$': ..., '^@/(.*)$': ..., '^erxes-api-shared/(.*)$': ... }` to `jest.config.ts`.
- **Files modified:** `backend/plugins/ai_api/jest.config.ts`.
- **Commit:** `1da746f73f` (Task 1 — caught when designing the test harness).
- **Result:** Tests resolve `erxes-api-shared/utils` (via `jest.mock()` in this plan) and `~/connectionResolvers` (via filesystem) correctly. `pnpm nx test ai_api` exits 0.
