### Shared library extensions (`frontend/libs/erxes-ui/src/ai/`)

**REQ UI-10 implementation (Task 3, 5 files + 1 modification):**

- **`useAIAvailable.ts`** — `function useAIAvailable(): { available: boolean | null; loading: boolean; refetch: () => void }`. On mount, calls a module-scope `probe()` that wraps `import('ai_ui/config')`. Resolves true on success, false on any rejection. Module-scope `Promise<boolean> | null` cache — single in-flight probe per page lifetime. `refetch()` clears the cache + bumps a `tick` state that the `useEffect` dependency picks up. Initial state `available: null, loading: true`. Hook **never throws** — all errors caught into `available: false`.
  - **Injection seam (`aiAvailableProbe.impl`)**: a module-exported mutable holder `{ impl: () => Promise<unknown> }`. Tests swap `aiAvailableProbe.impl` to control success/failure without `jest.resetModules()`. Production code never reassigns it. See "Deviations" §2 for rationale.
  - **`resetAIAvailableCache()`** — public export for tests + the Settings page's "Test Connection" flow (Phase 1.4) — clears the module-scope cache so the next consumer triggers a fresh probe.
- **`AiRemoteBoundary.tsx`** — `function AiRemoteBoundary({ children, fallback }: { children: ReactNode; fallback?: ReactNode })`. Wraps `react-error-boundary`'s `<ErrorBoundary>` (already in root `package.json` as `^5.0.0`). Default fallback: `<div data-ai-remote-boundary-fallback>AI features are unavailable.</div>` — the `data-ai-remote-boundary-fallback` attribute lets devs grep for unwrapped imports in dev tools. Custom fallback prop overrides. Catches synthetic throws from the Phase 1.1 hooks stubs (`useAIChat: implementation lands in Phase 3.2`) so misuse is graceful.
- **`index.ts`** — barrel: exports `useAIAvailable`, `resetAIAvailableCache`, `aiAvailableProbe` (test seam), `AIAvailability` type, `AiRemoteBoundary`, `AiRemoteBoundaryProps` type.
- **`__tests__/useAIAvailable.test.tsx`** — 3 cases: (1) probe resolves → eventually `available: true, loading: false`; (2) probe rejects → eventually `available: false, loading: false`; (3) `refetch()` clears the cache and a swapped-probe re-evaluates to a new result. All use the `aiAvailableProbe.impl` injection seam — no `jest.resetModules()`, no `jest.mock('ai_ui/config', ..., { virtual: true })`.
- **`__tests__/AiRemoteBoundary.test.tsx`** — 3 cases: (1) no-error children pass through; (2) throwing child renders the default fallback (`AI features are unavailable.`); (3) throwing child with custom `fallback={<span data-x>custom</span>}` renders the custom node. `console.error` is suppressed for the throw paths since react-error-boundary logs them by design.

## Deviations from Plan

### Auto-fixed Issues

**1. [Rule 3 — Blocking, test infrastructure] Switched from `jest.doMock` virtual-module pattern to injectable probe (`aiAvailableProbe.impl`)**

- **Found during:** Task 3 GREEN — the planned test pattern from `<behavior>` (`jest.mock('ai_ui/config', () => ({ default: {} }), { virtual: true })`) failed with `TypeError: Cannot read properties of null (reading 'useState')` on the third test (`refetch() clears cache`).
- **Root cause:** Calling `jest.resetModules()` between tests (required to swap the virtual mock for the refetch test) re-requires the hook in a fresh registry but `@testing-library/react`'s `renderHook` (top-level imported) still references the OLD React module instance. React's internal dispatcher state lives on the singleton React instance; when the hook closes over a DIFFERENT React (via the isolated registry's `require('react')`), `useState` reads the OLD React's dispatcher which is `null` outside of an active render. Same issue reproduced with `jest.isolateModules`.
- **Fix:** Refactored `useAIAvailable.ts` to indirect the dynamic import through a module-exported mutable holder `aiAvailableProbe = { impl: () => Promise<unknown> }`. Production code calls `aiAvailableProbe.impl()` which defaults to `import('ai_ui/config' as string)`. Tests swap `aiAvailableProbe.impl = () => Promise.resolve(...)` or `Promise.reject(...)` directly — no `jest.mock`, no `jest.resetModules`, no `jest.isolateModules`. The injection seam is documented in the source with a clear "test seam" comment. `resetAIAvailableCache()` is exported so the third test can clear the cache between probe swaps (and the Settings page's "Test Connection" flow gets this for free).
- **Why this is a Rule 3 fix not an architectural change:** The hook's PUBLIC contract is unchanged — consumers still see `useAIAvailable(): { available, loading, refetch }`. The injection seam is an internal implementation detail (the test seam holder is exported because TS strict mode rejects `(module.exports as any)` shenanigans, but production callers have no reason to touch it). The alternative — `jest.mock` with virtual modules — would force `jest.resetModules` which is known-broken with @testing-library/react when the hook closes over React.
- **Files modified:** `frontend/libs/erxes-ui/src/ai/useAIAvailable.ts` (added `aiAvailableProbe` export), `frontend/libs/erxes-ui/src/ai/__tests__/useAIAvailable.test.tsx` (uses the injection seam instead of virtual mocks), `frontend/libs/erxes-ui/src/ai/index.ts` (re-exports `aiAvailableProbe` + `resetAIAvailableCache`).
- **Commit:** `a98482c95e` (the GREEN commit folded both the source + the test-pattern fix; the RED commit `4096cc2eaf` still uses the original `jest.doMock` pattern from the plan as a snapshot).
- **Result:** 6/6 tests pass on the first re-run after the refactor. Zero TS errors.
