# Phase 1.1: Shared Module + Plugin Scaffolds - Context

**Gathered:** 2026-05-21
**Status:** Ready for planning

<domain>
## Phase Boundary

Stand up the cross-cutting foundation every later phase depends on — `erxes-api-shared/src/ai/` shared module, `ai_api`/`ai_ui` plugin skeletons mirroring `backend/plugins/sales_api/src/main.ts` and `frontend/plugins/sales_ui/module-federation.config.ts`, Docker base bump to `node:18.20-alpine`, and the typed graceful-disable shim so other plugins can compile against `trpc.ai.*` even when `ai` is excluded from `ENABLED_PLUGINS`. No business logic, no provider calls, no UI behavior — only the scaffolding that lets Phases 1.2+ proceed.

In scope: `src/ai/{shim,encryption,types,tokens,redaction,providers/base,providers/index}.ts`, `ai_api/` plugin skeleton with empty Apollo + tRPC routers, `ai_ui/` plugin skeleton with `./config` + `./aiSettings` + stub remotes, Dockerfile bump, `.env.sample` additions, `docker-compose.yml` Qdrant service, `ERXES_SECRET` validation, `useAIAvailable()` hook + `ErrorBoundary` pattern.

Out of scope: provider HTTP calls (Phase 1.2), audit log writes (Phase 1.3), settings UI rendering (Phase 1.4), tool registry (Phase 2.1), agent loop (Phase 2.2), automation (Phase 3.1). The scaffold compiles but does nothing useful on its own.

</domain>

<decisions>
## Implementation Decisions

### Module Path & Import Shape
- **D-01:** AI module lives at `backend/erxes-api-shared/src/ai/` — a new top-level peer to `/utils`, `/core-modules`, `/core-types`. Mirrors the brief's literal §3 layout. Add a corresponding `"./ai"` subpath export in `backend/erxes-api-shared/package.json` (preconstruct-managed) so consumers import via `from 'erxes-api-shared/ai'`. Update `backend/erxes-api-shared/tsconfig.json` and root `tsconfig.base.json` path alias `"erxes-api-shared/ai/*": ["backend/erxes-api-shared/src/ai/*"]`.
- **D-02:** No nesting under `utils/`. The brief's §6.2 example wording `from 'erxes-api-shared/utils/ai'` is treated as imprecise; we ship `from 'erxes-api-shared/ai'` exclusively. The `mountAiToolsRouter` helper (Phase 2.1) re-exports from the same module.

### Client API Ergonomics
- **D-03:** `createAIClient(subdomain)` is a **synchronous factory returning a typed JS Proxy** that lazily throws `AINotEnabledError` at the first actual method call. Shape: `const ai = createAIClient(subdomain); await ai.llm.chat({...})`. No null-checks at consumer call sites; no async factory ceremony. Error class lives at `erxes-api-shared/src/ai/shim.ts` with the message *"AI plugin not enabled. Add `ai` to ENABLED_PLUGINS and restart the gateway. Docs: …"* (link placeholder filled by Phase 3.2 docs pass).
- **D-04:** Detection of "AI is enabled" inside the proxy = check `ai` is present in the runtime-discovered plugin list (existing `service-discovery.ts` `getPlugins()` API, cache-keyed by subdomain, 60s TTL). Not by env-var inspection (which would miss multi-tenant deployments where some subdomains opt in differently in the future).
- **D-05:** The proxy surface in Phase 1.1 declares the **full** TypeScript shape (`{ llm: {...}, rag: {...}, agent: {...}, tools: {...}, prompt: {...}, audit: {...} }`) with every method signature stubbed to a proxy handler. No method implementations land in Phase 1.1 — every call throws `AINotEnabledError` until Phase 1.2 wires the first real route (`llm.chat`/`llm.embed`).

### Module Federation Expose Strategy
- **D-06:** Phase 1.1 ships the **final shape** of `ai_ui/module-federation.config.ts` with all 6 exposes declared: `./config`, `./aiSettings`, `./Copilot`, `./atoms`, `./hooks`, `./widgets`. Phases 2.3 and 3.2 fill in the placeholder modules, not the MF config.
- **D-07:** Phase 1.1 placeholder modules for the not-yet-built exposes return tiny inert components:
  - `./Copilot` → a `<></>` fragment with a `// stub: filled in Phase 2.3` comment
  - `./atoms` → an empty Jotai atom map `{}` with a typed shape
  - `./hooks` → object with stubs (`useAIChat: () => { throw new Error('Phase 3.2'); }`)
  - `./widgets` → object with stubs (`AISuggestButton: () => null` etc.)
- **D-08:** `shared` block in `ai_ui/module-federation.config.ts` mirrors `frontend/plugins/sales_ui/module-federation.config.ts:3-13` verbatim — `react`, `react-dom`, `react-router`, `react-router-dom`, `@apollo/client`, `jotai`, `ui-modules`, `erxes-ui`, `react-i18next` all listed; non-listed libs return `false`. Use `singleton: true, requiredVersion` from root `package.json`. NO `strictVersion: true` (per PITFALLS §P11 — tolerate minor drift).

### ERXES_SECRET Fail-Fast Scope
- **D-09:** `ERXES_SECRET >= 32 bytes` validation runs at `ai_api/src/main.ts` startup BEFORE `startPlugin({...})` is invoked. Failure throws with message *"ERXES_SECRET must be >= 32 hex bytes (got N). Generate with `openssl rand -hex 32`."* Process exits with code 1.
- **D-10:** Validation is NOT in `erxes-api-shared` startup — deployments running `ENABLED_PLUGINS=sales,frontline` (no `ai`) must boot without ever touching `ERXES_SECRET`. Lifecycle: only the `ai_api` service refuses to start.
- **D-11:** The shim's `createAIClient()` does NOT re-validate the secret. By the time a consumer reaches `createAIClient()`, either (a) `ai` is enabled and `ai_api` already validated, or (b) `ai` is disabled and the shim throws `AINotEnabledError` before any encryption ever happens.

### Cross-cutting Files (must-ship)
- **D-12:** Files to land in Phase 1.1 (per SUMMARY.md cross-cutting list):
  - `backend/erxes-api-shared/src/ai/index.ts` — re-exports public surface
  - `backend/erxes-api-shared/src/ai/shim.ts` — `createAIClient()` + `AINotEnabledError` (Proxy implementation)
  - `backend/erxes-api-shared/src/ai/encryption.ts` — `encryptSecret(plaintext, subdomain)` + `decryptSecret(ciphertext, subdomain)` using `scryptSync(ERXES_SECRET, subdomain, 32)` and AES-256-GCM envelope `{ version: 1, iv, ciphertext, authTag }` (base64-joined). Versioned envelope per PITFALLS §P14 Policy A (rotation script lands Phase 1.2; envelope format ships in 1.1 so we don't migrate later)
  - `backend/erxes-api-shared/src/ai/types.ts` — `ChatMessage`, `ToolDef`, `AiToolDef`, `Usage`, `ProviderError`, `AINotEnabledError`, all Zod schemas with `.strict()` (reject unknown fields — surface drift early)
  - `backend/erxes-api-shared/src/ai/providers/base.ts` — `ILLMProvider` interface (chat / embed / listModels) — no concrete implementations in Phase 1.1
  - `backend/erxes-api-shared/src/ai/providers/index.ts` — exports interface, empty registry shape
  - `backend/erxes-api-shared/src/ai/tokens.ts` — static `COST_TABLE` keyed by `(providerKind, modelId)` with `inputCostPer1M`/`outputCostPer1M`, plus `DRIFT_MULTIPLIER` map (per PITFALLS §P7: openai 1.0, anthropic 1.15, google 1.10, azure 1.0, ollama 1.10, custom 1.20). Eager `tiktoken` init at module load (gated behind `process.env.NODE_ENV !== 'test'` so unit tests don't pay for it)
  - `backend/erxes-api-shared/src/ai/redaction.ts` — `redactKey()` regex (covers OpenAI `sk-`, Anthropic `sk-ant-`, Groq `gsk_`, Google `AIza...`, 32-hex Azure) + thin wrapper around `redact-pii-light@1.0.0` for `redactPii(text)` / `rehydratePii(text, map)`
  - `backend/plugins/ai_api/` — full skeleton (Dockerfile uses `node:18.20-alpine`, `project.json`, `tsconfig.json`, `tsconfig.spec.json`, `jest.config.ts`, `src/main.ts` calling `startPlugin({ name: 'ai', port: 3320, graphql: ..., expressRouter: ..., hasSubscriptions: true })` with empty resolvers/router but valid types)
  - `backend/plugins/ai_api/src/{connectionResolvers.ts, routes.ts, apollo/{typeDefs,resolvers,subscription}, trpc/{init-trpc, routers}, modules, meta/, workers/}` — directories created with `.gitkeep` or minimal index files
  - `frontend/plugins/ai_ui/` — full skeleton (`module-federation.config.ts`, `rspack.config.ts`, `project.json`, `tsconfig.json`, `src/{main.ts, bootstrap.tsx, config.tsx, modules/Main.tsx}`) mirroring `frontend/plugins/sales_ui/`
  - `frontend/plugins/ai_ui/src/config.tsx` — exports `CONFIG: IUIConfig` with `settingsNavigation` callback registering an AI Settings entry (target route stub `/settings/ai`)
  - `frontend/plugins/ai_ui/src/widgets/index.ts` + `hooks/index.ts` + `atoms/index.ts` — placeholder exports per D-07
  - `frontend/plugins/ai_ui/src/Copilot.tsx` — stub component returning a `<></>`
  - `frontend/libs/erxes-ui/src/ai/useAIAvailable.ts` (or under `ui-modules/`) — **MF-load probe**: tries `import('ai_ui/config')` inside a memoized async, sets `available = false` on rejection. Cached for the lifetime of the host page. Re-evaluated on navigation only if the user explicitly retries
  - `ai_api/Dockerfile` — base image `node:18.20-alpine` (NOT 18.16)
  - `docker-compose.yml` — append an optional `qdrant` service profile (gated via `profiles: [ai]`) so `docker compose up` doesn't start it by default
  - `.env.sample` — append `AI_API_PORT=3320`, `AI_UI_PORT=3020`, `ERXES_SECRET=`, `AI_DEFAULT_VECTOR_BACKEND=qdrant`, `QDRANT_URL=http://localhost:6333`, `AI_EMBED_CONCURRENCY=4`, `AI_DEFAULT_CHAT_MODEL=`, `AI_DEFAULT_EMBED_MODEL=`, `AI_BUDGET_DEFAULT_USD=50`, `AI_MAX_TOOL_STEPS=8`, `AI_GUARDRAILS_STRICT=false`
  - `ENABLED_PLUGINS` example in `.env.sample` comment shows `ai,sales,frontline,...`
- **D-13:** `package.json` additions in `erxes-api-shared` for Phase 1.1: **only the dev-time dependencies that the shared types need** — `tiktoken@1.0.22`, `@anthropic-ai/tokenizer@0.0.4`, `redact-pii-light@1.0.0`, `zod-to-json-schema@3.23.5` (pinned exact). Provider SDKs (`openai@6.38.0`, `@anthropic-ai/sdk@0.97.1`, `@google/generative-ai@0.24.1`) land in Phase 1.2 alongside the concrete provider adapters — Phase 1.1 only needs `ILLMProvider` interface, no implementations.

### Plugin Scaffold Method (Claude's Discretion)
- **D-14:** Use **manual copy of `backend/plugins/sales_api/` + `frontend/plugins/sales_ui/`** as templates (not `pnpm create-plugin ai`). Rationale: the generator creates an example "module" pattern that doesn't fit the AI Kernel shape; manual lets us strip the example product/module immediately. Document this choice in `CLAUDE.md` for any future plugin-kernel that won't use the generator.

### Test Coverage Floor for Phase 1.1
- **D-15:** Phase 1.1 ships unit tests for `encryption.ts` (round-trip per subdomain; cross-subdomain decrypt fails), `redaction.ts` (each provider's key pattern redacted), `shim.ts` (proxy throws AINotEnabledError when `ai` not in plugin list; doesn't throw when present). Provider adapter tests, agent loop tests, budget tests all land in their owning phases. Target line coverage on `src/ai/` >= 80%; XCUT-05's >70% on `ai_api/src/modules/` accrues across PR1.

### Claude's Discretion
- Exact filename and export-list inside `src/ai/index.ts` (named re-exports — planner decides between `export * from './shim'` vs explicit named exports).
- Whether `ErrorBoundary` lives in `erxes-ui` or `ui-modules` — pick the one that matches the existing pattern for cross-plugin shared components.
- Whether `useAIAvailable()` exposes a manual `refetch()` method — leaning yes for the Settings page's "Test connection" flow, but planner can defer to Phase 1.4 if simpler.
- Lockfile: planner runs `pnpm install` once after adding deps; commit the lockfile churn.

## Existing Code Insights

### Reusable Assets
- **`startPlugin({...})`** at `backend/erxes-api-shared/src/utils/start-plugin.ts` — used as-is. `meta` keys we extend later (Phase 2.1 adds `aiTools`).
- **`getPlugins()` / `getPlugin(name)` / `isEnabled(name)`** at `backend/erxes-api-shared/src/utils/service-discovery.ts:126-198` — used by the shim's "is AI enabled" detection (D-04).
- **`graphqlPubsub` singleton** at `backend/erxes-api-shared/src/utils/graphqlPubSub.ts` — types referenced by `ChatMessage` / `Usage` in `src/ai/types.ts` for the future streaming subscription shape (Phase 1.3 wires the resolver).
- **`IUIConfig` + `settingsNavigation` callback** at `frontend/libs/erxes-ui/src/types/UIConfig.ts` — defines the contract for AI Settings injection.
- **`@module-federation/enhanced` Rspack config** in every existing plugin — pattern for the `shared` block is in `frontend/plugins/sales_ui/module-federation.config.ts`.

### Established Patterns
- **Plugin self-registers via Redis on boot.** No central manifest; the gateway discovers via `joinErxesGateway`. Our `ai_api` registers like any other plugin.
- **TypeScript path aliases** in `tsconfig.base.json` map `erxes-api-shared/*` to `backend/erxes-api-shared/src/*` (verified in CLAUDE.md). Adding `"erxes-api-shared/ai/*"` mirrors this.
- **`preconstruct` builds CJS + ESM** for `erxes-api-shared`. Adding a subpath export requires both `package.json` `exports` map entry AND a `preconstruct.entrypoints` entry (verify in `backend/erxes-api-shared/package.json`).
- **Dockerfiles copy from `dist/` after `pnpm nx build`.** No tooling change in 1.1 beyond base image bump.

### Integration Points
- **Gateway boot** picks up `ai_api` via existing Redis service-discovery once it's in `ENABLED_PLUGINS`. No gateway code changes in Phase 1.1.
- **Apollo Federation supergraph** — gateway composes our typeDefs (empty in 1.1) automatically. Apollo Router accepts subgraphs with no types? Verify during planning (`type _Empty { _: Boolean }` placeholder may be required).
- **Frontend host (`core-ui`)** discovers `ai_ui` remote at boot via the existing plugin-config API. No host changes — `ai_ui` registers itself in the plugin-config table the host queries.
- **`docker-compose.yml`** — new optional Qdrant service uses `profiles: [ai]` so `docker compose up` (no profile) keeps existing dev workflow unchanged.

<specifics>
## Specific Ideas

- The shim's error message must include a docs link placeholder that Phase 3.2 fills in. Phase 1.1 ships `…/docs/ai-plugin-setup` as a TODO link.
- `redactKey()` regex must include all 5 patterns from PITFALLS §P1: OpenAI `sk-`, Anthropic `sk-ant-`, Groq `gsk_`, Google `AIza`, Azure 32-hex.
- Tokens cost table is **per-`(providerKind, modelId)` keyed**, with admin overrides at `ai_models` collection later (Phase 1.3); 1.1 only ships the static defaults.
- `eslint-plugin-import` rule: forbid `import { x } from 'sales_api'` / `'frontline_api'` / etc. inside `backend/plugins/ai_api/` — enforces the registry-only discovery rule. Add the rule in Phase 1.1 even though there's nothing to enforce yet.
- The MF `ErrorBoundary` pattern is documented in PITFALLS.md and CONCERNS.md as a known gap in the existing codebase — fixing it specifically for `ai_ui` remote imports is in scope; fixing it for all other remotes is NOT (separate phase / separate concern).
- `useAIAvailable()` re-evaluation policy: cached for the lifetime of the host page, manual `refetch()` exposed for the Test Connection flow.

</specifics>
