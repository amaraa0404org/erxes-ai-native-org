## Module Path & Import Shape

| Option | Description | Selected |
|--------|-------------|----------|
| `src/ai/` — `from 'erxes-api-shared/ai'` | Top-level peer to /utils, /core-modules, /core-types. Matches brief's literal §3 wording. New aspect = new top-level. | ✓ |
| `src/utils/ai/` — `from 'erxes-api-shared/utils/ai'` | Nested under existing utils. Symmetric with utils/redis.ts, utils/mq-worker.ts. The brief uses this form in §6.2's `mountAiToolsRouter` example. | |
| Hybrid — split by audience | Plugin-facing helpers under /utils/ai; internal kernel-only pieces under /ai. Two import paths to remember. | |

**User's choice:** `src/ai/` (top-level)
**Notes:** AI is a new top-level aspect of the system, not a utility. Cleaner mental model for downstream developers; `from 'erxes-api-shared/ai'` reads as "AI surface" not "AI utility." The §6.2 inconsistency in the brief is treated as imprecise wording.

## Client API Ergonomics

| Option | Description | Selected |
|--------|-------------|----------|
| Lazy proxy | `const ai = createAIClient(subdomain); await ai.llm.chat({...})`. Sync factory returns a Proxy that throws AINotEnabledError at the actual method call. | ✓ |
| Async factory | `const ai = await getAIClient(subdomain); if (!ai) return; await ai.llm.chat({...})`. Factory does a health check and returns null when AI is disabled. | |
| Static module exports + capability check | `import * as ai from 'erxes-api-shared/ai'; if (await ai.isAvailable()) ai.llm.chat({subdomain, ...})`. No proxy magic. | |

**User's choice:** Lazy proxy
**Notes:** Terse at the call site; consumers don't have to thread `if-null` checks through their resolvers. AINotEnabledError surfaces at the same point any other tRPC error would. Detection of "is AI enabled" uses the existing service-discovery `isEnabled(name)` API rather than env-var inspection (so future multi-tenant per-subdomain opt-in is possible).

## MF Expose Strategy

| Option | Description | Selected |
|--------|-------------|----------|
| Final shape Day 1 with stub modules | Phase 1.1 ships the full exposes list (`./config, ./aiSettings, ./Copilot, ./atoms, ./hooks, ./widgets`). Phases 2.3 / 3.2 only fill in stubs. | ✓ |
| Progressive (one expose per phase) | Phase 1.1 ships only `./config` and `./aiSettings`. Phase 2.3 adds `./Copilot, ./atoms`. Phase 3.2 adds `./hooks, ./widgets`. | |

**User's choice:** Final shape Day 1
**Notes:** Stable MF contract from day 1 means consumers can write lazy imports today (typed) and have them activate as later phases ship. Avoids three rounds of MF cache invalidation across the milestone. Cost: 4 placeholder modules in PR 1, each <10 LOC.

## ERXES_SECRET Fail-Fast Scope

| Option | Description | Selected |
|--------|-------------|----------|
| Only ai_api startup + lazy in shim | `ai_api/src/main.ts` validates at boot. Non-AI deployments (`ENABLED_PLUGINS=sales,frontline`) boot cleanly without setting ERXES_SECRET. | ✓ |
| `erxes-api-shared` startup hook (every service refuses) | Validates the secret on every service that imports erxes-api-shared (= all of them). Forces every deployment to set ERXES_SECRET even if `ai` is never enabled. | |
| Lazy at first encrypt() call only | Defer validation until the first provider save. Zero startup impact. Failure manifests at the worst moment (admin creates first provider). | |

**User's choice:** Only ai_api startup + lazy in shim
**Notes:** Aligns with the "plugin must be optional" constraint from PROJECT.md. Validation happens before `startPlugin()` is called inside `ai_api/src/main.ts`. The shim doesn't re-validate — if `ai` is in `ENABLED_PLUGINS`, `ai_api` already ran the check; if not, the shim throws AINotEnabledError before any encryption is ever attempted.

## Claude's Discretion

- Exact filename and export-list inside `src/ai/index.ts` (named re-exports vs `export *`).
- Whether `ErrorBoundary` lives in `erxes-ui` or `ui-modules` — pick whichever matches the existing pattern for cross-plugin shared components.
- Whether `useAIAvailable()` exposes a manual `refetch()` method — leaning yes for the Phase 1.4 Test Connection flow, but planner can defer if simpler.
- Lockfile churn: planner runs `pnpm install` once after deps land; commit the lockfile.
- Plugin scaffold method: manual copy of `sales_api` / `sales_ui` as templates (not `pnpm create-plugin ai`) — the generator creates an "example module" pattern that doesn't fit the AI Kernel shape; manual is more surgical.
- `useAIAvailable()` detection mechanism: MF-load probe (try `import('ai_ui/config')`, set false on rejection). Health-ping via tRPC adds a network round trip per page; capability flag requires host changes. MF-probe is simplest and the only one that detects MF version mismatch.
