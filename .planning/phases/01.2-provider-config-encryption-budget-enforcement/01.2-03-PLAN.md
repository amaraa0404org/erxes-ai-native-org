<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| ProviderConstructorArgs.apiKey → SDK client | Decrypted key crosses into the SDK's internal state. Discipline: never reflect back via `this.apiKey`. |
| SDK error.toString() → application logs | P1 — the most common leak surface. Mitigation: every error path runs through `redactKey()` before bubbling up. |
| Azure deploymentName / apiVersion → URL construction | Non-secret config; safe to log. |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-01.2-11 | Information Disclosure (P1) | OpenAI/Anthropic SDK error chains | mitigate | Every `catch` block calls `redactKey(message)` and wraps as `ProviderError({ providerKind, model, statusCode, code, message: redactedMessage })`. Tests 3 + 8 prove the sanitized output contains zero substring matches for `sk-`, `sk-ant-`, `gsk_`, `AIza`, or 32-hex. |
| T-01.2-12 | Information Disclosure | `this.apiKey` retention | mitigate | Constructor passes `args.apiKey` to `new OpenAI({ apiKey })` and never assigns to `this.apiKey`. The SDK retains it as private state. Adapters discard the local reference. |
| T-01.2-13 | Tampering | Azure deploymentName injection | accept | `config.deploymentName` is validated as non-empty string by the constructor; the SDK constructs `${endpoint}/openai/deployments/${deploymentName}/...` URLs internally. Injection requires modifying the encrypted provider doc, which requires admin DB access (out of scope). |
| T-01.2-14 | DoS | testConnection() runaway | accept | Each adapter's testConnection issues exactly one HTTPS request (`models.list` or a 1-token chat probe). No retries within the adapter (Phase 1.3 adds exponential backoff at the chat/embed layer). Plan 05 owns the per-user rate limit (D-07). |
| T-01.2-SC | Tampering | npm/yarn registry — openai, @anthropic-ai/sdk | accept | Both first-party vendor packages (OpenAI Inc., Anthropic) — same threat profile as Plan 01 T-01.2-SC. |
</threat_model>
