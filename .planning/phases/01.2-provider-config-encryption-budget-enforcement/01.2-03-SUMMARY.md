# Phase 01.2 Plan 03: OpenAI/Anthropic/Azure Provider Adapters Summary

**Three concrete ILLMProvider adapters (OpenAI, Anthropic, Azure) implementing real listModels + testConnection against pinned vendor SDKs, PROVIDER_REGISTRY populated, P1 key-leakage acceptance gate enforced by three dedicated auth-failure tests.**

## Accomplishments

- **OpenAIProvider (real listModels + testConnection):** wraps `openai@6.38.0`. `listModels()` calls `client.models.list()` and maps each model id through an in-module prefix→capability heuristic table (gpt-4o → 128k chat/vision/tools, gpt-4 → 128k chat/tools, gpt-3.5 → 16k chat/tools, text-embedding-3 → 8k embed-only, o1-/o3- → 128k chat, default → 4k chat). `testConnection()` is a latency-timed wrapper around `listModels()`.
- **AnthropicProvider (real models.list + static fallback):** wraps `@anthropic-ai/sdk@0.97.1`. The pinned SDK exposes `client.models.list()` — that's the primary path. A static three-Claude-model table is kept as the fallback for a hypothetical future SDK downgrade, gated by `typeof maybeList !== 'function'` and a `TypeError`-on-call detector. Vision capability is derived from `capabilities.image_input.supported === true`; chat + tools are always added; embed is never added (Anthropic has no embeddings endpoint).
- **AzureProvider (config-validated, deployment-scoped):** wraps `AzureOpenAI` from the same `openai` package. Constructor validates `config.deploymentName` AND `config.apiVersion` (throws with a descriptive message on either missing). `listModels()` returns a single ModelInfo for the configured deployment (Azure lacks a clean SDK-exposed listing endpoint). `testConnection()` issues a one-token chat-completion probe (`max_tokens: 1`, `'ping'`) against the deployment — the only honest reachability check given the listing limitation.
- **PROVIDER_REGISTRY signature evolution:** Phase 1.1's `() => ILLMProvider` became `(args: ProviderConstructorArgs) => ILLMProvider`. Three entries populated; google/ollama/custom remain undefined for Plan 04. The Phase 1.1 `surface.test.ts` had its single registry assertion swapped for the now-populated check.
- **P1 acceptance gate enforced at the adapter layer:** three auth-failure tests (one per adapter) build an SDK error whose `.message` contains a leaky key substring, run the adapter through `testConnection()`, then `JSON.stringify(result)` and assert NO substring matches any of redactKey's 5 patterns (`sk-`, `sk-ant-`, `gsk_`, `AIza`, 32-hex). All three pass.
- **Test count + coverage:** 16 new tests in `providers-openai-family.test.ts` (covers OpenAI 5x, Azure 5x, Anthropic 4x, registry 2x). Coverage on `src/ai/providers/`: 86.48% statements / 87.05% lines / 96.96% functions — well above the 70% milestone floor. `openai.ts` 91.48% stmts; `anthropic.ts` 88.13% stmts; `azure.ts` 76.31% stmts (uncovered span is the error-path message branch that the auth-failure test exercises but doesn't fully traverse). `providers/index.ts` 100%.

## Decisions Made

- **Capability heuristic table lives in `openai.ts`, NOT in `tokens.ts`:** the prefix-to-capability mapping must work for arbitrary models the provider returns (including fine-tuned variants like `ft:gpt-4o:org::xyz`), which `COST_TABLE` (a per-exact-model lookup for cost data) does not cover. Documented in the openai.ts header.
- **Azure deployment-as-model:** `listModels()` returns one ModelInfo with `id: deploymentName`. The trade-off (Azure has no per-deployment models endpoint in the SDK; full listing requires Azure Resource Manager IAM that is out of scope) is documented in the file header. Phase 1.4 will surface this limitation in the Settings UI.
- **Azure testConnection probes via 1-token chat:** because `listModels()` cannot fail in our implementation (it returns a hard-coded singleton), the only honest reachability check is to actually call the deployment. `max_tokens: 1` keeps quota impact minimal.
- **TypeScript any-casts on SDK error shapes:** the sanitize helpers use `(e as any)?.status` / `(e as any)?.message` because the openai + anthropic SDKs do not export their error shape types in a way that's safely assignable across the duck-typed test mocks. The risk is bounded — the helper only ever READS these fields with typeof guards, never WRITES.
- **Test file is monolithic:** all 16 tests live in `providers-openai-family.test.ts` rather than splitting per-adapter. The shared mock factory setup is non-trivial (jest.mock must run before any adapter import); splitting would duplicate it three times.
