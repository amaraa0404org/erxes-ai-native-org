type AiProvider @key(fields: "_id") {

  apiVersion: String

  aiProvider(_id: ID!): AiProvider

tRPC routers — providers:
```typescript
export const providersRouter = t.router({
  providers: t.router({
    list: t.procedure.query(async ({ ctx }) => { /* providerQueries.aiProviders */ }),
    get: t.procedure.input(z.object({ _id: z.string() })).query(async ({ ctx, input }) => { /* providerQueries.aiProvider */ }),
    add: t.procedure.input(aiProvidersAddInputSchema).mutation(...),
    edit: t.procedure.input(z.object({ _id: z.string(), doc: aiProvidersEditInputSchema })).mutation(...),
    remove: t.procedure.input(z.object({ _id: z.string() })).mutation(...),
    test: t.procedure.input(aiProvidersTestInputSchema).mutation(...),
  }),
});
```

Same shape for `modelsRouter` and `budgetsRouter` — single-namespace routers merged into appRouter.

The `IContext` type for tRPC procedures is `AiTRPCContext = ITRPCContext<{ models: IModels }>` (already declared in Phase 1.1's `init-trpc.ts`). tRPC procedures do NOT have `checkPermission` automatically — internal callers (other plugins, the shim, internal scripts) bypass it. For Phase 1.2 the Apollo path is the externally-reachable surface; tRPC is internal-only. We do NOT replicate `checkPermission` calls in tRPC procedures (the Plan 05/06/07 resolver-level `checkPermission` calls run when invoked via Apollo; tRPC procedures call lower-level service functions directly).

Practical mapping:
- Apollo `aiProvidersAdd` resolver → calls `providerMutations.aiProvidersAdd` (which has `checkPermission`)
- tRPC `providers.add` → calls `models.AiProviders.createProvider(encryptApiKeyAtBoundary(parsed, subdomain))` directly (no permission check; internal-only surface)

The internal tRPC surface is what Phase 1.3 `trpc.ai.llm.chat` will call when it needs `checkBudget`. Phase 1.2 ships the budget tRPC procedures so Phase 1.3 can wire them without modifying init-trpc.ts again.
